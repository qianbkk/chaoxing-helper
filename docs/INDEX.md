# docs/ —— 文档索引

本项目所有**结论、取证与设计决策**都沉淀在这里。文档分三种读法：

- 按**角色**读（我要用 / 我要改 / 我想知道某个结论怎么来的）→ 看第一节；
- 按**问题**查（我想知道 X）→ 看第二节速查表；
- 想知道**改东西时该守什么规矩**→ 看第四节文档纪律。

本仓库的公开版从 v1.9.0 起独立演进；早期版本（v1.1~v1.8.2）的产物与补丁脚本保存在私有存档仓库，
结论部分已经整理进本目录。

## 一、按角色的阅读顺序

### ① 我要用这个脚本（只想装上跑起来）

1. [安装与自动更新.md](安装与自动更新.md) —— 装 ScriptCat → 导入脚本 → 填 AI 配置，一步不缺；
2. 想知道「这类脚本为什么普遍做不了题、我们改了什么」→ [AI答题改造方案.md](AI答题改造方案.md) §0 一句话结论；
3. 想知道「现在到底哪些能用、哪些还没做」→ [AI答题改造方案.md](AI答题改造方案.md) §3（未实现项）
   与 [v1.4章节测验与字体解密说明.md](v1.4章节测验与字体解密说明.md) §5（未验证清单）。

### ② 我要改这个项目

1. [开发与构建.md](开发与构建.md) —— 构建链、补丁链约定、测试、发布流程；
2. 不知道从哪儿下手 → [开发与构建.md](开发与构建.md) §「常见任务」：
   加模块改 `src/modules/`、加版本改 `src/patches/`、加命令改调试通道，都在那一张表里；
   **动 `src/modules/` 前先看**
   [../src/README.md](../src/README.md) §「模块文件：活源码 vs 历史快照」——
   那里 21 个文件里只有 7 个是构建输入，改错文件等于没改；
3. 改完要同步哪些东西 → 本文件第四节「文档纪律」，以及
   [开发与构建.md](开发与构建.md) §「日常流程」里的重建 + 全测两步。

### ③ 我想知道某个结论是怎么来的

1. 先在第二节速查表里按问题定位到「哪份文档的哪一节」；
2. 想看**整体脉络**（为什么这么设计、放弃了什么）→ [AI答题改造方案.md](AI答题改造方案.md)；
3. 想看**排查过程与实测证据**（日志、截图、⚠️ 更正）→ [v1.4章节测验与字体解密说明.md](v1.4章节测验与字体解密说明.md)；
4. 想看**这个项目从哪来、现在干不干净**→ [来源与安全说明.md](来源与安全说明.md)。

## 四、文档纪律

1. **结论要有依据**：写「某实现有/没有某功能」这类判断，必须附**依据位置（章节 / 行号）或实测命令与输出**；
2. **未验证就写未验证**：不能把「代码写完了」写成「功能可用」；
3. **改代码同步改文档**：改了行为就要更新对应文档的「未验证清单 / 结论」；
4. **文档只增不改历史结论**：发现旧结论错了，用「⚠️ 更正」的方式标注，并说明更正依据，不静默抹掉；
5. **公开仓库红线**：文档里也不许出现挖矿载荷与他人的个人信息，脱敏后仍要保留结论；
6. **新增文档先更新本索引**，保持「2 步内能找到任何东西」。
