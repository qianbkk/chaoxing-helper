## 1. 背景：v1.2 最初的移植版字体解密是**死代码**

### 1.1 问题

超星把题干和选项用自定义字体（`@font-face font-cxsecret`）加密显示，DOM 里读到的是乱码，例如：

```
DOM 原文：蒝栗腐败问题慁慃挑战
真实内容：面对腐败问题严峻挑战
```

不还原就**既查不到题库、也让 AI 读不懂题目** —— 这是"题库命中率低"的隐藏主因。

v1.2 从 GF 530068 移植了这段逻辑，**但最初的移植版只搬了"调用逻辑"，没带上它依赖的三样东西**：
字体解析库 Typr、md5、以及字形映射表。于是 `decrypt()` 每次都在"TyprRef 或 md5Ref 不存在"处直接 `return false`，
**解密从未真正执行过** —— 一段看起来完整、实际不工作的代码。

### 1.2 影响

- 题库收到的题干是乱码 → 必然查不到 → 命中率被压到接近 0；
- AI 收到的题干也是乱码 → 模型只能瞎猜；
- v1.3 的考试端模块同样继承了这个缺陷（它复用同一套解密入口）。

## 2. 字体解密自包含化

### 2.1 补齐的三项依赖

| 依赖 | 文件 | 大小 | 来源 | 许可 |
|---|---|---|---|---|
| Typr（字体解析） + md5 | `src/assets/typr-md5.min.js` | 38,066 B | 与早期版本 `@require` 的是同一款库 | MIT |
| 字形映射表 table 2.0 | `src/assets/font-table-2.0.json` | 355,427 B | 早期版本的 `@resource` | MIT（author `wyn665817`，version `20220515.1`） |

两项都由早期的打包脚本与 v1.4 增量脚本**内联进脚本**，
脚本因此**完全自包含**，不依赖 `@require` / `@resource` 任何外部资源（私有仓库也无法匿名拉取外部资源）。

> 📌 v1.9.0 起，这道闸门由 `src/tools/verify-baseline-font-table.cjs` 承担：直接核对**基线里内联的那张表**
> 与 `src/assets/font-table-2.0.json` 是否逐条一致 —— 两者失配的后果是**静默**的（字体解密不命中、题干全是乱码）。

### 2.2 映射表的打包格式

原始 JSON 是 `{字形路径md5后8位 : 标准Unicode码点}`，直接内联 355 KB 太胖。
打包脚本把它压成**每条 6 字节**的二进制再 base64：

```
key   : 4 字节大端 uint32（字形路径 md5 的后 8 位十六进制）
value : 2 字节大端 uint16（标准 Unicode 码点）
```

```
20902 条 → 原始 125,412 字节 → base64 167,216 字节
```

发布件里 base64 占 **28.5%**（167,216 / 587,047）。运行时用 `atob` + `Uint8Array` 解包成查表对象。

算法与最初的移植版一致：`md5(JSON.stringify(glyphPath)).slice(24)` → 查表 → 标准码点。

### 2.3 实测证据

2026-11-24 在真实超星作业页（`/mooc-ans/work/doHomeWorkNew`，西安航空学院 · 形势与政策 2026秋）：

- 该页 **40 个加密字符全部命中映射表，40/40**，题干与选项还原正确；
- 证据形态：逐字符的 md5 与命中结果（`蒝=…/7b688f1c`、`栗=…/8bfebc3b` …），未加密的普通字符标为 `NG`（非字形）；
- **仓库内可复现的证据（两份）**：
  - `tests/fixtures/font-cxsecret.b64` —— 从真实页面抓下来的加密字体，
    单测用它跑解密，逐字断言还原结果 —— 任何人 clone 后 `node tests/workauto-module.test.js` 都能复跑；
  - `tests/fixtures/font-decrypt-evidence.txt` —— 该页 168 个字符的逐字命中记录，
    其中加密字符全部命中（40/40），普通字符标 `NG`。

> ⚠️ 解密**只在读取文本时按需进行，不改写页面 DOM**。
> 选项 `<li>` 里含有 `input` 控件，改 `innerHTML` 会把选项一起删掉。

## 3. 新增「章节测验 / 作业自动作答」模块

代码在 `src/modules/workauto.v1.4.js`（17 KB），由 v1.4 的增量脚本插入到字体解密模块之后。

### 3.1 最初的移植版为什么在当前超星上完全失效

早期沿用的（2024 版）答题分支只认 `work/phone/doHomeWork` 这类旧地址，题目结构也写死在
`.Py-mian1` / `.answerList` / `li[id-param]` 上。而当前超星真实结构是：

```
地址：/mooc-ans/work/doHomeWorkNew?courseId=...&workId=...
题目：div.TiMu > div.Zy_TItle > div.clearfix.font-cxsecret.fontLabel   ← 题干（加密字体）
选项：ul.Zy_ulTop > li > input[name=answerXXXXX][type=radio|checkbox][value=字母]
                           + a.after                                        ← 选项文字（加密字体）
题型：input[name^=answertype][value=0单选 / 1多选 / 3判断]
提交：a.Btn_blue_1.workBtnIndex
```

**那套分支与选择器在这套结构上一个都不匹配** ⇒ 章节测验自动答题等于失效。
（`mooc2/work/dowork` 旧结构同样在模块的 `matchPage` 覆盖范围内。）

### 3.2 关键坑：超星会打乱选项顺序

页面 hidden input `randomOptions=true`，超星会把选项顺序随机打乱，
于是**显示的字母 ≠ `input[value]`（原始字母）**：

```
显示：A=猎狐   B=打虎   C=拍蝇   D=天网行动
真实：input.value 分别是 C / B / D / A
```

而题库（icodef）返回的是**选项文字**（多选用 `#` 分隔），不是字母。
因此本模块**一律"按选项文字"匹配**，天然不受乱序影响；
万一题库只返回字母，才按 `input.value`（原始字母）回退匹配 —— 与题库存储口径一致。

### 3.3 答题链路与提交策略

```
收集题目（题干/选项先解密）
   ↓ 题库 icodef（多选按 # 分隔，逐项按文字匹配）
   ↓ 未命中 / 超时 / 流控(-2)
   ↓ AI 兜底（复用 v1.1 的 aiAsk，返回选项序号，按下标点击）
   ↓ 仍无结果 → 随机兜底（单选选第一个，多选全选）
```

**提交策略（保守）**：只有**每道题都拿到题库或 AI 的答案**时才点提交；
只要有题是随机兜底的，本次就**不自动提交**，避免把错误答案交错交上去。

### 3.4 面板

新增独立面板区块「章节测验 / 作业自动作答」，两个开关：

| 开关 | 存储键 | 默认 | 作用 |
|---|---|---|---|
| 章节测验/作业自动作答 | `unrivalWorkAuto` | **开** | 进新版作业页即自动识别并作答 |
| 全部题目有依据时自动提交 | `unrivalWorkSubmit` | **开** | 满足 §3.3 条件时自动点提交 |

与 v1.3 的三个「附加功能（实验性 · 未验证）」不同：**本模块默认开启**，
因为它的页面识别与字体解密部分已在真实超星页上实测。

### 3.5 与 AI 链路的衔接

`collectOptions` 增加了新版作业页分支（`.TiMu > ul.Zy_ulTop > li`）。
不加这个分支，学习端的 AI 兜底在作业页上取不到选项，无法使用。

### 6.2.3 查出的两个真缺陷（已修）

**缺陷 A：`max_tokens` 被思考 token 吃光 ⇒ 该题作不出来**

- 现象：5 题里偶发 1 题 `AI返回内容为空`。
- 根因：MiniMax M3 系列的**思考无法关闭**，且**思考 token 计入 `max_tokens`**；
  脚本原本发 `max_tokens: 300`，思考一长就把额度吃光，返回 `finish_reason=length` + 空 `content`。
  证据就是报错里的 `finish_reason=length`（v1.4.1 把这个字段加进了报错信息）。
- 修法（v1.4.1 / v1.4.2）：
  1. `max_tokens` 300 → 8000（上限，不是预留额度，模型答完即停，不增加开销）；
  2. 对 MiniMax 端点额外下发 `reasoning_effort: 'low'` ——
     MiniMax 官方给的办法就是「降低思考深度」而不是关闭思考；
     其他厂商的 OpenAI 兼容层不认这个字段，所以**只在 `baseUrl` 命中 `minimax` 时才带**。

**缺陷 B：沿用的正确率公式先取整再乘 100 ⇒ 一题没答对就永远不提交**

沿用的原式：`Math.floor((totalQuestionNum - questionNum) / autoQuestionNum) * 100 >= accuracy`
—— 先做除法再 `floor`，比例只要小于 1 就算成 0，正确率永远是 0% ⇒ **自动提交永不触发**；
必须 5 题全部由 AI/题库答出（`questionNum` 减到 0，比值才等于 1）才会走提交分支。

这解释了「答了 4/5 却只保存不提交」。本次**未改动这段公式**（属既有行为，改动要另外评估），
而是通过把 AI 的空内容问题修掉，让每道题都能拿到答案 ⇒ 命中既有的 100% 分支 ⇒ 正常提交。

对照 3.3~3.6 与 4.1，流程都完整（答完 → 已提交答案 → 提交后回报 → 所有任务处理完毕 → 翻章），

#### 6.2.9.2 根因：沿用的「先取整再乘 100」假正确率被当成了决定依据

```
build:4184  if (autoQuestionNum > 0 && Math.floor((totalQuestionNum - questionNum) / autoQuestionNum) * 100 >= accuracy && _w.top
build:4185      .unrivalAutoSubmit == '1') {
                  → 提交（乐观日志「正确率符合标准，已提交答案」）
build:4197  } else if (_w.top.unrivalAutoSave == 1) {
build:4198      _w.top.unrivalWorkInfo = '正确率不符合标准或未设置自动提交，已自动保存答案';
build:4199      _w.top.jump = true;                       ← 无条件跳走
build:4200      if (autoQuestionNum > 0 && Math.floor(...) * 100 > 0) {   ← 同一个假判定
build:4203          _w.noSubmit();                      ← 条件不成立 ⇒ 根本没保存
              }
              }
```

三个问题叠在一起：

1. **这个「正确率」不是正确率**：分子是「已作答数」、分母是「可自动作答题数」，
   衡量的是「自动题答完了没有」。v1.1 当初改分母是为了避开「填空题撑大分母导致永远达不到门槛」，
   结果换了个新坑（§6.2.3 缺陷 B 记的就是这件事）。
2. **`Math.floor` 把未完成状态压成 0**：只要还有自动题没答上，比值就 < 1 → floor 成 0 →
   `0 >= accuracy(80)` 不成立 → 必然走「不达标」分支。
3. **「不达标」分支既跳走又不保存**：`jump = true` 是无条件的，而保存被同一个假判定的 `> 0` 挡住
   ⇒ **既没保存也没提交**，章节被直接丢过去，任务点永远不亮。

**触发时机**：`busyThread` 归零的那一刻。而 `busyThread` 的记账（每个请求回调扣 1）
与 `questionNum` 的口径（每答上一题扣 1）并不严格对应，归零可能早于「最后一题点完」——
3.2 就是：第 2 题的 AI 答案在 0.8 秒后才到，脚本却在这一秒判定结束并跳走了。

#### 6.2.9.3 v1.8.1 的修法

- 判定改成**以 DOM 实况为准**：选项 `li` 的 `class` 含 `cur` 才算这题答上了（与既有实现点选项时用的标记一致）；
- 还有题没答上 → **继续等**（最多 60 秒，每 10 秒报一次「已答 N/M」），**绝不提前跳走**；
- 等满 60 秒仍未答上的题 → 用兜底选项补齐（点第一个选项），保证提交时没有空题；
- 提交条件由假正确率换成「DOM 完成率 ≥ 正确率门槛」；
- 「自动保存」分支：**先保存、再跳走**（既有实现是先 `jump`、2 秒后才保存，两者抢跑，翻页常把保存打断）；
- `busyThread` 判断由 `!= 0` 放宽为 `> 0`（万一被重复扣成负数，不会永久卡住）。

> ⚠️ **这条修复尚未在真实超星页复验** —— 需要装上 v1.8.1 后重跑 3.2。
>
> 另外要说清楚：v1.8.1 只是**不再拿那句假正确率当判定依据**，
> 并没有把「答对了多少」这个真实正确率算出来（那要读超星返回的成绩，属另一件事）。

### 6.2.10 v1.8.2：自主跟随更新 + 直播/阅读研究探针

#### 6.2.10.1 版本自检通知的空参 bug（v1.7 遗留）

**现象**：接收端检测到新版本时，脚本日志打出

```
★ 发现新版本 ?： —— 在脚本猫里打开该地址点「安装」即可升级
```

版本号和地址都是空的。

**根因是两端协议不一致**（不是某端写错了一个字段，是两边用了两套格式）：

| 端 | 原来怎么发/收 |
|---|---|
| 接收端 `src/tools/log-sink.cjs` | 发**对象字段**：`{cmd:'newversion', version:'…', url:'…'}` |
| 脚本 `src/modules/debugcmd.v1.7.js` | 按**字符串**解析：`cmd` 用空格分隔出参数数组 |

命令名 `newversion` 收到了（所以流程能跑到底），但 `arg[0]`（版本）、`arg[1]`（地址）
全是 `undefined` ⇒ 两个参数都丢。

**修法（v1.8.2）**：接收端改发**字符串命令** `newversion <版本> <地址>`；
脚本端同时兼容两种传参（`arg[0] || c.version`、`arg[1] || c.url`）。
任一端单独改格式都不会再把对方搞挂。

#### 6.2.10.2 ScriptCat 原生更新器的真实要求（读源码确认，2026-11-24）

读 `scriptscat/scriptcat` main 分支源码，逐条确认：

| 要求 | 出处 | 结论 |
|---|---|---|
| 两个地址必须同时声明 | `src/pkg/utils/script.ts`：`if (metadata.updateurl && metadata.downloadurl)` | 只声明一个**不生效** |
| 不声明时怎么推算 | `deriveMetaUrl = (url) => url.replace("user.js", "meta.js")` | 我们必然 404 ⇒ 静默「已是最新」 |
| `@updateURL` 返回什么 | `src/app/service/service_worker/script.ts`：`fetchScriptBody(url)` → `parseMetadata(code)` | 必须是 **meta.js 的「==UserScript== 元数据块」**，**不是** Greasy Fork 的 JSON |
| `@downloadURL` 返回什么 | 同上，`url = script.downloadUrl \|\| script.checkUpdateUrl` | 完整脚本 |
| 版本比较 | `src/pkg/utils/semver.ts` 的 `versionCompare` | 分段比较，非数字段按字符串比 ⇒ `1.8.2-AI > 1.8.1-AI` 成立 |
| 能否抓本机地址 | `src/manifest.json`：`host_permissions: ["<all_urls>"]` | 可以 |
| `.user.js` 会被劫持进安装页 | DNR `regexFilter: "^([^?#]+?\\.user(\\.bg|\\.sub)?\\.js)"` + `redirect.regexSubstitution` | `GM_openInTab` 打开安装地址即可弹出安装页 |
| `GM_openInTab` 是否受支持 | `src/pkg/utils/script_compat.ts` 的 `REGISTERED_GRANTS` | 受支持 |

> 上游 issue [#1840](https://github.com/scriptscat/scriptcat/issues/1840) 记录了同一机制；
> 维护者已在 #1845 修复「检查失败却误显示为『已是最新』」的显示问题，
> 但**推算出的 meta.js 不存在**这件事本身没变 —— 要用原生更新器必须显式声明。

**实测**（直接用 ScriptCat 源码里的 `parseMetadata` 正则与 `versionCompare` 函数跑本机地址）：

- `parseMetadata()` 解析成功：`@version 1.8.2-AI`、`@name`、`@updateURL`、`@downloadURL` 都取到；
- 版本比较：`1.8.2-AI` 相对 `1.8.0-AI`/`1.8.1-AI`/`1.7.0-AI` 判定「有更新」，相对 `1.9.0-AI` 判定「更旧」。

**地址设计**：由接收端从 `dist/` **动态提供**，用固定地址而不是带版本号的文件名 ——
脚本升级后这两个地址也不用改：

```
http://127.0.0.1:8124/latest.meta.js   ← 检查更新用（只有元数据块）
http://127.0.0.1:8124/latest.user.js   ← 下载用（完整脚本）
```

**不在 `dist/` 里放别名副本** —— 「`dist/` 只留当前发布件」这条规矩不破。

#### 6.2.10.3 直播/阅读：现有认知与下一步

**已确认的事实**：

1. **直播/阅读这两类任务，此前一直没有实现**
   - 早期基线（GF 484657 v5.0）与参考的较新实现（GF 530068 v5.5.9.9.6）都只处理
     `video` / `document` / `workid` 三种 type；
   - 我们的日志里的 `[live]` / `[read]` 是 v1.6 打的类型标记并自动暂停。
2. **GF 530068 里有完整的「阅读助手模块」**（上游源码不再随包分发，在线地址见
   [来源与安全说明.md](来源与安全说明.md) §1）：
   识别 `/ztnodedetailcontroller/visitnodedetail` 阅读正文页 + 阅读任务目录页，
   保持页面滚动（`timerInterval`），**全程没有任何网络请求** ——
   说明超星的阅读时长靠**页面自身**上报，脚本只要让页面活着并滚动就能计时。
3. **直播此前同样没有实现**，超星到底校验什么（时长 / 心跳 / 人机交互）**完全未知**。

**因此定下的做法**：不猜着写实现，先加探针。
`dump` 命令（v1.8.2 新增）输出五段：

| 段 | 内容 | 用途 |
|---|---|---|
| `URL` / `TITLE` | 当前页地址与标题 | 确认在哪个章节 |
| `attachments` | `type`·`job`·`passed`·`name`·`jobid`·`objectid`·`workid`·`property` 键名 | **直播/阅读的 type 到底是什么** |
| `阅读/直播链接` | 指向 `ztnodedetail`/`visitnodedetail`/`live` 的链接 | 阅读正文页入口形态 |
| `iframe` | 所有 iframe 的 id 与 src | 是不是塞在 iframe 里 |
| `missionList` | 脚本自己认出来的任务 | 能对上就说明脚本已在处理 |

**结构上做成可扩展的探针组**：每个探针是独立小方法 `_probeXxx()`，`dump()` 按顺序拼接；
以后要查新的东西，加一个探针方法、再往 `dump()` 的列表里加一行即可，**不用改动已有探针**。

> ⚠️ **全部未验证** —— `dump` 的探针内容还没在真实超星直播/阅读章节上跑过，
> 直播/阅读的自动化实现本版也没做。需要装上 v1.8.2 后用命令通道实测。
